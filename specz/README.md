# Specz 插件

当前版本：`2.4.0`

Specz 是面向高能力编码模型的轻量工程状态协议。它不替代模型的规划和验证能力，也不把普通编码任务包装成 bundle；只有任务需要跨会话恢复、多智能体协作、用户审批或可审计证据时，才外部化最小必要状态。

## 核心原则

**让模型负责思考，让 Specz 负责保存模型容易遗失的工程状态。**

- 普通任务默认直接检查、实现和验证，不创建 bundle。
- 不使用文件数、模块数或改动行数划分任务规模。
- 检查点和治理任务只维护一个中文 `状态.md` 作为执行账本；需要持久化设计时另用《评审说明》，两者不重复记进度。
- 执行按依赖就绪的任务或紧耦合模块分步推进，可安全时并行。
- 子智能体、独立复验和归档都是按收益或风险选择的能力，不是固定阶段。
- 设计涉及关键权衡、共享契约、评审或跨会话复用时，可在分析与任务拆分中生成结构化《评审说明》，不把它变成每个任务的必经阶段。
- 计划可以根据新代码事实修正；用户目标、确认决策和安全边界不可擅自改变。

## 使用形态

| 形态 | 适用场景 | 持久化内容 |
|---|---|---|
| 直接执行 | 当前上下文可以完成并验证 | 不创建 bundle |
| 检查点 | 跨会话恢复或多任务协作 | 目标、任务状态、写入范围、证据、下一步 |
| 治理 | 审批、高风险或审计场景 | 检查点内容，加批准、风险和关键证据 |

## 设计文档

`specz-brief` 是独立的可选设计文档技能。它从用户目标和真实代码形成当前方案，写成可供实现、协作与评审的中文《评审说明》，不要求用户先提供完整设计；评审是用途之一，而不是生成文档的前提。

- 有活动 bundle：写入 `specs/<中文任务名>/评审说明.md`。
- 没有 bundle：优先使用用户指定路径，否则写入 `docs/<中文方案名>-评审说明.md`。
- 文档以“功能与设计主线”为正文，每个功能点一次讲完功能要求、设计落点、边界和验证，其他章节通过功能点编号关联，不重复改写。
- 按界面、服务、数据或集成的实际变更选择评审细节；图可选页面/状态流、分层交互或数据流，简单局部修改不强制画图。
- 接口方法、真实路径和 SQL 必须来自代码或契约事实，无法确认时明确标记，不能按功能名猜测。
- 涉及上线、迁移、配置、脚本、灰度、监控或回滚时，按需增加上线与回退模块。
- 关键决策必须包含备选、理由和影响；实施前的验证只能写为计划验证。
- 设计文档只放当前有效方案，不保存任务拆分、负责人或步骤状态；这些由 `状态.md` 独占维护并只链接设计文档。
- 生成评审文档不创建状态账本、不批准方案，也不自动实施。

## Bundle

只有检查点和治理路径创建：

```text
specs/
└── <中文任务名>/
    ├── 状态.md
    └── 评审说明.md  （设计需要独立保留时）
```

bundle 名、文件名和正文全部使用中文。Specz 不要求 `spec.md`、`design.md`、`tasks.md`、`verification.md` 或 archive；独立设计有评审、协作或恢复价值时才生成 `评审说明.md`。如果团队已有 ADR、PR 和 CI，直接链接这些事实来源，不复制内容。

## 与 Specx 的区别

- **Specz**：适合规划、验证和工具判断能力较强的模型，默认放权，只提供按需状态协议。
- **Specx**：适合需要明确阶段、模板、检查点和修复循环的轻量模型，保留完整规范工作流。

## 安装

Claude Code：

```text
/plugin marketplace add https://github.com/Y2138/zz-agent-plugins
```

Codex 按仓库根目录 `codex-plugin-add.md` 合并 marketplace，不覆盖已有插件配置。

Pi Coding Agent 从仓库根目录安装时会同时发现 Specz 与 Specx 的 skills；只有 Specx 保留 workflow reminder extension。
