# Specz Brief

从用户目标、代码事实与 agent 的方案分析形成当前有效设计，并写成可独立阅读、可核实、可直接讲述的中文设计文档；需要时可直接作为评审材料。不要求用户先给出完整方案，沿一条主线讲完功能要求、设计落点、边界和验证，避免按章节反复改写同一内容。

## 启动与返回契约

只接受两种入口：

- **Specz 委派**：父流程已接管当前任务，并明确交接目标、交付意图、当前位置、账本路径或无账本说明、设计来源、输出路径和返回位置。缺少这些内部上下文时先返回父流程补齐，不向用户索要流程元数据。
- **用户显式调用**：用户明确要求使用 `specz-brief`。无需启用 Specz 或创建账本；按用户目标生成独立文档，完成后交付。

不满足任一入口时不加载模板、不写文档，回到当前任务原流程。用户只说“做技术方案”“生成设计文档”或“准备评审材料”，以及目录中存在旧 bundle，都不是独立启动条件。

在父流程中，设计与范围冲突、必须由用户作出的决定和缺失授权由 Specz 处理；本技能汇报具体缺口，不自行推进实现或改写账本。独立显式调用时，阻塞性产品问题才直接向用户询问。

## 输入与输出

按需读取当前用户要求、已确认决策、活动 bundle 的 `状态.md`、相关代码与配置、产品或设计稿、接口或数据契约、实施范围、验证计划和发布信息。

- Specz 委派：沿用父流程给出的已有或目标路径，已有文档按本次设计缺口更新。
- 用户独立显式调用：使用用户指定路径，否则写入 `docs/<中文方案名>-评审说明.md`；只有用户明确指定当前 bundle 时写入其目录。

方案名、输出文件名和正文使用中文。必须写入文件，不能只在聊天中返回草稿。只处理交接中的一个方案，不创建或扫描 bundle，不修改 `状态.md` 或产品代码；由父流程在账本中登记文档引用。

## 信息准备

写文档前确认至少具备：明确目标、范围边界、可根据现有事实形成的核心方案、可观察验收信号。若方案尚未形成，先分析目标与代码并提出当前设计，不要求用户替 agent 完成方案设计。

- 已有上下文足够时不要重复提问。
- 事实优先从代码、配置和现有文档核实。
- 会改变设计结论的缺失信息，按主题归纳少量阻塞问题并按启动契约交给父流程或用户。
- 不阻塞成文的未知项写 `待补充`，并在最终反馈中集中列出。
- 不用通用最佳实践填补事实、方案或发布信息的缺口。
- agent 形成的方案默认标为“待评审”；只有用户明确确认后才将文档状态写为“已确认”。

内容权威顺序：当前用户目标和已确认决策 > 仓库指令与代码事实 > `状态.md` > 当前方案与验证计划 > 假设。来源冲突且影响范围、行为、兼容性或验收时标记 `【待确认】`，不得擅自选择。

## 单主线组织

只记录当前有效方案与最终结论，不记录演进过程、讨论流水或已淘汰方案。默认用“功能与设计主线”承载正文，每个功能点一次讲完：

```markdown
| 功能点 | 场景与功能要求 | 设计落点 | 边界与兼容 | 验证信号 |
|---|---|---|---|---|
| F-01 | 用户如何触发、系统应产生什么结果 | 哪些组件如何协作实现 | 异常、默认值和不变契约 | 如何观察功能成立 |
```

- 按用户路径、业务环节或可独立验收的能力拆行；简单修改只写一行。
- “场景与功能要求”使用业务语言，只写触发、规则和可见结果。
- “设计落点”按实际变更写页面与组件、交互与状态、前后端职责、服务处理或数据流；不默认以接口、表和 SQL 为中心，也不复述功能要求。
- “边界与兼容”只写相关的异常、权限、输入校验、不同屏幕或设备、旧数据与旧调用等约束。
- “验证信号”写可观察结果；实施前标记为计划验证，只有可复查证据才写已通过。
- 其他章节引用 `F-01` 等编号，不重新描述对应功能和设计。

### 信息唯一归属

| 信息 | 唯一归属 |
|---|---|
| 为什么做、主要影响、需要什么决定 | 评审结论 |
| 用户要求、系统结果和实现落点 | 功能与设计主线 |
| 影响方案选择的存量事实 | 现状约束 |
| 存在权衡的选择、理由和代价 | 关键设计决策 |
| 真实接口、数据、配置或脚本增量 | 工程变化 |
| 跨功能专项回归、性能或安全验证 | 专项验证与回归 |
| 发布、生产验证和恢复操作 | 上线与回退 |
| 真实风险和未决问题 | 风险与待确认事项 |

同一事实只在其归属位置完整表达一次。其他位置需要关联时使用功能点编号或章节引用，不做同义改写。评审结论只保留一句话目标和一句话核心方案，不写正文摘要。

### 按变更类型补足评审信息

- 界面或交互：核实入口与导航、布局或组件复用、操作路径、加载/空/错误/禁用/成功状态、表单规则、响应式与可访问性中实际受影响的部分。主线写关键行为；状态多且会影响评审时，才使用模板中的“交互状态与界面约束”，只补主线未展开的差异。设计稿、截图或现有组件无法核实时按影响标记 `待补充` 或 `【待确认】`，不臆造视觉规格。
- 服务或数据：核实权限与校验、状态变化、契约、持久化、失败处理和兼容；接口及数据库细节仅在确有变更时进入“工程变化”。
- 全栈或集成：写清前后端校验分工、数据与错误如何传递、外部依赖或异步结果如何回到用户可见状态；交互状态与接口明细各归其位，不复制一遍功能流程。
- 非页面任务：用调用方或业务触发代替“用户操作”；不强制 UI 状态、设计稿、接口、数据库或图。

## 图示

默认最多生成一张主线图：交互设计可用页面/状态流，跨层方案可用组件或泳道图，数据变化可用关系或流转图；只画评审需要理解的顺序、责任或关键分支。图应补充主表难以表达的关系，不逐行复刻主表。

- 简单字段、常量、配置或单模块局部修改不画图。
- 只有业务状态流与复杂技术链路都需要独立评审时才生成第二张图。
- 面向业务的泳道不出现表字段、数值枚举、SQL、接口路径、脚本任务、函数类名、消息主题或代码分支。
- 技术泳道可使用已核实的技术标识，但不展开成函数级调用图。

## 技术事实

- 接口方法与路径只能来自接口文档、OpenAPI、路由定义、控制器注解或代码；无法确认时写 `待补充（未确认真实接口地址）`，不得按功能名推断。
- 只有确有数据库变更或 SQL 评审需要时才写数据库设计；SQL 集中放在其中，按 DDL、索引、初始化或回填、检查、回滚排序。涉及查询效率但缺乏证据时写 `待补充`，不要让前端方案填“无数据库变更”的占位章节。
- 普通业务词、模块名和状态值不使用行内代码；只对真实文件、符号、配置键、命令、HTTP 方法与路径等技术标识使用代码格式。
- 文档不保存任务拆分、负责人、步骤进度或执行证据；有活动账本时由 `状态.md` 独占维护。设计中的“计划验证”是验收思路，不是执行状态。

## 模板与可选模块

始终读取并使用 [评审文档模板](references/评审文档模板.md)。涉及上线、数据库迁移、配置变更、脚本或任务、灰度、监控告警、生产验证或回滚时，再读取并插入 [上线与回退模块](references/上线与回退模块.md)。

保留模板必填章节，删除不适用的条件章节和所有占位符。用 **加粗** 标记关键结论和关键决策；用 `【事实】`、`【已确认】`、`【方案】`、`【假设】`、`【待确认】` 在可能混淆时区分信息性质。

## 工作流

1. 检查启动契约，沿用父流程交接的当前设计与代码事实，补足本次需要的方案；独立显式调用时从用户目标形成设计。
2. 收集并核实最小必要信息，批量处理缺失项。
3. 识别界面、服务、数据或集成的实际变更，按用户路径或业务环节生成唯一的功能与设计主线。
4. 只为主线无法承载的事实保留条件章节，并按需插入上线与回退模块。
5. 写入评审文档，执行语义去重自检，只修正文档。
6. 返回绝对路径、当前设计摘要、`待补充` 与 `【待确认】` 缺口、未确认接口，以及文档自检结果。父流程据此继续原任务位置，不把文档自检当作实现验证。

## 自检

- 文件存在，讲述者可以沿功能与设计主线一次讲完要求、设计、边界和验证。
- 每项主要信息只有一个完整表达位置；删除其他章节中的同义句后不损失信息。
- 没有独立的需求目的、业务逻辑或方案描述段落再次复述主线。
- 评审结论不超过四个短条目，且不展开正文细节。
- 关键设计决策只包含真实权衡，不复述普通实现步骤。
- 图只补充顺序、责任或分支，不复制表格文字；简单方案不生成装饰性图表。
- 界面方案有必要的交互状态与可观察反馈，非界面方案不留空 UI 栏目；任何视觉和技术标识都可追溯到输入或标为待确认。
- 接口方法与路径均有真实来源或明确标为未确认；SQL 只出现在数据库设计中。
- 专项验证只写主线验证信号之外的跨功能覆盖，并通过功能点编号关联。
- 不出现与 `状态.md` 重复的任务表、负责人、步骤进度或执行日志；设计调整只保留当前有效方案。
- 需要上线治理时包含发布顺序、生产验证、监控和回退；否则不保留空上线章节。
- 全文为中文，无未替换占位符、空章节、大段背景或内部实现流水。

Specz 委派完成后始终返回父流程，由 Specz 决定交付、等待必要确认或继续执行；不得因文档状态为“待评审”而自动结束工程任务。独立显式调用完成后交付文档；后续实现仍由用户请求和当前工程流程决定。
