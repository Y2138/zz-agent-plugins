# project-design-md · 存量项目 DESIGN.md 提取

从已有前端项目中提取轻量 `DESIGN.md`。本 skill 只负责把项目 UI 风格文档化，不负责生成原型、实现页面或打包长期可复用资产。

## 目标

产出一份可被 agent 和团队成员快速消费的项目级设计契约，回答：

- 这个项目的视觉气质是什么
- 主色、背景、文字、边框、状态色如何分工
- 字体、字号、字重、密度和间距有什么规律
- 按钮、输入、表格、导航、卡片、弹层等组件是什么形状和状态语言
- 页面布局、信息密度、响应式和外壳结构有什么习惯
- 后续生成或评审新页面时应遵守哪些 prompt hints

## 适用场景

- 旧项目没有可读设计规范，但需要沉淀统一的 UI 语言
- 需要让后续页面方案、原型或代码实现遵守现有项目风格
- 需要把代码、CSS、截图和运行页面里的视觉规则压缩成 `DESIGN.md`
- 需要在重构、扩展模块或多人协作前统一“这个项目应该长什么样”

## 不适用

- 不根据产品原型图再生成 HTML 原型
- 不把页面截图直接翻译成生产代码
- 不抽取完整组件 API、业务字段、路由、状态管理或工程架构
- 不生成 `assets/`、示例 HTML、组件脚手架或项目专属 skill
- 不凭少量截图发明完整设计系统

## 输入门禁

至少需要一种可信 UI 证据，优先级从高到低：

1. 可运行页面或浏览器截图
2. 样式入口、CSS 变量、主题配置、Tailwind 配置或 token 文件
3. 核心组件源码或组件库使用方式
4. 设计稿、设计文档、Storybook、截图集
5. 用户提供的关键页面说明

证据至少覆盖：

- 页面外壳：顶栏、侧栏、导航、内容区
- 一个核心内容页：列表、详情、表单、仪表盘或工作台
- 常见控件：按钮、输入、选择器、表格/列表、反馈状态

**CHECKPOINT 1：** 证据不足时先列缺口并索取最小补充，不生成最终 `DESIGN.md`。

## 工作流程

### Phase 1 · 收集证据

1. 阅读项目入口、样式配置、主题文件、全局 CSS、组件库依赖和关键页面源码
2. 如有运行页面或截图，优先从真实渲染结果确认颜色、密度、布局和组件状态
3. 记录证据来源，区分 high / medium / low 置信度
4. 只收集影响视觉契约的信息，跳过业务逻辑和工程实现细节

### Phase 2 · 提取 UI 语言

提取轻量规则，不做穷举。

- 视觉气质：3-5 个形容词 + 关键特征
- 颜色角色：Primary、Accent、Background、Surface、Text、Border、State
- 字体规则：字体族、字号层级、字重、行高、数字/表格文本习惯
- 组件气质：按钮、输入、选择器、表格、导航、卡片、弹层、反馈
- 布局原则：页面外壳、栅格/宽度、间距节奏、信息密度、响应式倾向
- 交互模式：hover、focus、selected、disabled、loading、empty、error、confirm
- 反模式：项目中不应引入的视觉风格

每条重要规则尽量写成：

```text
规则 -> 证据 -> 置信度 -> 例外/待确认
```

### Phase 3 · 冲突处理

当不同页面或文件出现风格冲突：

1. 以当前主路径、最新页面、真实渲染证据为优先
2. 旧版页面、历史样式或局部异常写入“例外”
3. 无法判断时标为“待确认”，不要静默合并

### Phase 4 · 生成 DESIGN.md

输出项目级 `DESIGN.md`，结构固定为：

```markdown
# Design System: [项目名]

## 1. Visual Theme & Atmosphere
## 2. Color Palette & Roles
## 3. Typography Rules
## 4. Component Stylings
## 5. Layout Principles
## 6. Interaction Patterns
## 7. Prompt Hints
## 8. Evidence & Confidence
```

写作要求：

- 使用语义化命名，例如 `Operation Blue (#3B5BFF)`，不要只写 `blue`
- 写“如何使用”和“不要怎么用”，不要只列 token
- 控制篇幅，默认 1500-3000 字；证据不足时更短
- `Prompt Hints` 面向后续页面生成，直接写可复用提示片段
- `Evidence & Confidence` 说明来源、覆盖范围、低置信度规则和待确认项

### Phase 5 · 交付说明

交付时同时说明：

- 使用了哪些证据
- 覆盖了哪些页面类型和组件
- 哪些规则置信度低
- 哪些地方需要用户补充截图、运行页面或设计资料
- 这份 `DESIGN.md` 可用于后续页面方案、原型生成或 UI 评审，但不能替代完整设计系统

## 输出

默认只输出一个文件：

```text
DESIGN.md
```

除非用户明确要求，不创建其它文档、示例、HTML、assets 或脚手架。

## 质量门

交付前自查：

- 是否只产出 `DESIGN.md`
- 是否没有生成 HTML、assets 或项目专属 skill
- 是否覆盖 7 个核心设计段落和 Evidence & Confidence
- 是否把 token 写成语义化角色，而不是原始颜色清单
- 是否说明了证据来源、覆盖范围和置信度
- 是否区分主规则、例外和待确认项
- 是否包含后续生成页面可直接使用的 prompt hints

## 失败模式与兜底

- 证据不足：输出缺口清单和最小补充请求，不写最终 `DESIGN.md`
- 只有单张截图：可写草稿，但必须标低置信度，不声称代表完整项目
- 项目无法运行：用源码、样式配置和截图交叉验证，并标注限制
- 样式冲突严重：先输出冲突摘要，让用户确认主风格
- 没有明确 token：从真实 UI 观察中提取语义角色，避免假装存在官方 token

## 反例黑名单

- 不为了完整而穷举所有 CSS 变量
- 不提取路由、API、状态管理、权限模型或业务流程
- 不把组件源码说明写成组件 API 文档
- 不输出页面级需求说明冒充项目级设计契约
- 不用营销页、官网或通用 SaaS 模板替代真实项目风格
- 不在证据不足时写确定性结论
